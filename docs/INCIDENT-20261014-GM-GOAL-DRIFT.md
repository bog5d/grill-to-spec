# 反面案例 GM-2026-10-14｜目标漂移导致“测试通过、业务零产出”

> 分类：集团级 Goal-Drift Incident / P0 治理事故。本文只沉淀可公开的架构教训；项目原始生产证据存放于受访问控制的业务仓。不是「AI 无法自主工作」的通用结论。

## 董事长实际提出的目标
交付一个能在发起人不再发消息、开发会话结束后，持续领取工作、启动真实执行器、产生实际成果、独立验收、自动接棒、可恢复的 AI 总经理。

## 2026-10-14 审计观察（历史快照，不冒充当前状态）
- 开发汇报曾称 15 项验收中 11 项通过，且在进行 72 小时观察；这只是局部工程进度，不是终局能力达成率。
- 被观察的脚本仅采集宿主状态、心跳和安全信息；没有启动真实总经理、派工或安排开发任务。**72 小时观察对象与终局目标不同**。
- 真实运行侧存在双调度权威、执行器调用失败后反复尝试、监管循环重启但健康信号显示正常；缺少真实工作包产出与自动接棒。
- 「进程存活」与「业务有效」是两个独立命题。本案例证明此前**未验证无人值守自主工作**，不意味着已证明架构永远无法实现。

## 根因类别（原因判断，待产品仓具体复核）
1. **Goal 替身**：把“72 小时心跳/安全观察”当成“72 小时无人干预持续干活”。
2. **Gate 替身**：隔离单测或文档 PASS 替代真实控制器→执行器→成果→Gate→接棒全链。
3. **State 替身**：RUNNING/进程/日志更新替代有效业务进展。
4. **治理缺位**：没有持续展示“最终用户目标缺口”；开发指标与验收指标相互独立却混报进度。

## 对所有工程仓的强制反例回归
- 说「自动」：验证真实触发源、持久队列、无人确认时的自动下一步。
- 说「无人值守」：验证**开发会话退出**后的真实工作链，不能靠 bot 正在施工。
- 说「长跑」：核实运行时长中实际跑的是什么，任务产出、人工介入、心跳间隙各是多少。
- 说「健康」：核对有效运行配置、重复失败、启动/重启风暴、僵尸状态、真实工作结果。
- 说「百分比」：先固定目标、权重、硬门槛和证据规则；不能用子测试通过项占比代表用户可见效果。
- 说「完成」：分清代码 / 测试 / 合并 / 部署 / 运行 / 业务效果，分别给证据。

## 制度闭环与传达
集团中央规范：SCP v3.8；项目仓保留自己的 Goal Contract / HARNESS / Evidence，不复制规范全文；高风险项目用 CI 结构 Gate + 独立语义验收双门；回归样本至少包含“心跳全绿但任务零产出”的负样本。每个 GM/Agent 相关项目都要对照此案例出一份自查表：是否同类目标漂移、当前状态、有无整改 issue/负责人/截止 Gate。只有出示实际业务链证据才算事故关闭。
